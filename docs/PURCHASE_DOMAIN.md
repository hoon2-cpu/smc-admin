# 구매·정산 도메인 지식 (Purchase Module 설계 입력자료)

> 6~7단계(SSOT 데이터 아키텍처 + Purchase Module) 설계의 근거 자료.
> **핵심 원칙**: Purchase DB = Single Source of Truth. 월마감=Module, 정산=Output.
> 아래 코드/분류/항목은 **하드코딩하지 않고 Master/Setting에서 관리**(코드 수정 없이 추가 가능).

## 1. 업무 프로세스 (현행 As-Is)

기존 흐름:
1. 구매 요청자가 **아마란스 구매품의서 상신**
2. 결재라인 승인 → 총무팀이 해당 건 **구매** → 합의 승인 완료
3. **월마감** 시, **법인카드 사용내역을 아마란스에서 시트로 복붙** (카드사별 시트 별개)
4. 품의 없이 구매한 내역 등은 **개별 체크 / 별도 체크시트**로 관리

## 2. Purchase DB 유입 소스 (3가지)

1. **아마란스 품의 기반 구매** (승인 → 구매 → 합의) — 카드 사용내역 **Excel Import**
2. **품의 없는 정산 항목** — 예: **명함·네임택 구매** 등. 별도 엑셀이 아니라 **직접등록(수기 입력)** 경로로 Purchase DB 적재
3. **정기지출** (렌탈·리스·통신·임대 등 매월 반복 → **자동 생성**). 항목은 **추후 추가/삭제 가능** → Master 관리

## 3. 카드사 복붙 시트 형식 (a~m, 13열 고정)

| 열 | 항목 | 매핑(Master) |
| --- | --- | --- |
| a | 용도코드 | Purpose_Master |
| b | 부서코드 | Department_Master |
| c | 프로젝트코드 | Project_Master |
| d | 내용 | (자유 텍스트) |
| e | 거래처코드 | Vendor_Master |
| f | 거래처명 | Vendor_Master |
| g | 공급가액 | (금액) |
| h | 부가세 | (금액) |
| i | 거래일자 | (날짜) |
| j | 증빙코드 | Evidence(증빙)_Master |
| k | 지급기한(요청일) | (날짜) |
| l | 사원코드 | Employee_Master |
| m | 증빙번호 | (식별자) |

- **카드사마다 시트가 별개**지만 형식은 동일 → 소스는 여러 개, **Import 매핑 규칙은 하나**.
- 형식이 바뀌면 **Rule(매핑)만 수정**, Purchase DB 스키마는 불변.
- **대상 카드사**: (현재) **롯데카드, 하나카드** — **추후 추가 예정**. → `Card_Master`로 관리하고 Import는 카드사 수에 무관하게 동작.

## 5. 설계 요구 (요구 D)

- 형식·과정·항목이 추가/변경되어도 **시스템설정(Master)에서 추가**할 수 있어야 함 → 코드 재배포 불필요.
- 이는 SSOT 원칙의 **변경 격리(Adaptation Layer)**와 정확히 일치:
  - 변동성 큰 것 = Import 매핑(Rule), Export 양식(Template), 분류/코드(Master) → **설정으로 관리**
  - 안정적인 것 = **Purchase DB 스키마** → 고정

## 6. 다음 설계 시 확정할 것 (6~7단계)

- Purchase DB 정규화 스키마 (소스 3종을 하나로 흡수: source 구분 + 13열 정규화 + 분류/구분 + 상태 + 금액/날짜/증빙)
- Master 테이블 목록·키 (Purpose/Department/Project/Vendor/Evidence/Employee/Card + 마감종류/구분/정기지출)
- Import 매핑 규칙(카드사 시트 a~m → Purchase DB), 정기지출 자동생성 규칙
- Output(월마감 시트 월별 탭 / 아마란스 정산품의) 템플릿
- 모듈 간 읽기 계약 (Dashboard/Asset/Statistics가 Purchase DB를 참조하는 방식)
